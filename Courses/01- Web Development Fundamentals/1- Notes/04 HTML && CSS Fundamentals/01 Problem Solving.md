# How to learn to code
## Translating Mainframes and Specifications into Code

To get from the specifications to a fully implemented web page, there is a large amount of work that must be done, and this is typically done without any kind of roadmap. Here are just a few of the things that you, as the developer, often have to figure out. You may have to figure these things out on your own, or in collaboration with other teammates.

- **How should I organize the code? What files will I need to create or use to implement this project?** You will need to figure out the architecture, styles, and conventions that the team uses, and make sure you are following them as you contribute to the codebase.
    
- **What's the best way to organize the elements on the page?** You will need to map out which elements will be used for each piece of content on the page, and you will have to make decisions on how elements are grouped together. These decisions will be important when you start styling the page.
    
- **How should I deal with the details that are _not_ specified in the wireframe?** Many important details, such as the amount of whitespace between elements, will not be specified for you. You will need to do your best to make decisions that look similar to the wireframe, and are visually appealing.
    
- **How will I make sure the page is responsive on multiple screen sizes?** This is an important detail on any project, as many wireframes include designs for a web and a mobile version. There might be content and organization differences between the two. It will be up to you to thoroughly test your page on multiple screen sizes to make sure everything looks and works as it should regardless of the screen size of the user.

## Using Experimentation and Problem-Solving to Get the Job Done

Feeling overwhelmed yet? At this stage, early in the project, it can be easy to start feeling frustrated about the amount of gray area, or the number of unanswered questions related to the project. You might start questioning your technical abilities, wondering if you really "have what it takes" to get the job done. It may be tempting to procrastinate and dwell on these feelings, but it is better to jump right in and start getting some code on the screen and start seeing some elements show up in the browser.

Remember Polya? Now is a good time to review the four steps of the problem solving process, which will be helpful for moving forward on any project. Then, take a look at these more specific strategies that you can use to move forward through unfamiliar territory. These are the very same strategies that developers use on the job, and the strategies you will need to use as you navigate the HTML and CSS portion of this prepwork.

## Start with the most basic elements or placeholders

You can start making progress by getting the largest elements on the page. In the images above, we can see that App Academy's landing page has a navigation bar on top, some text on the right and a large image on the left. There are other details, but these are the main "chunks" of the page to layout and focus on first. You can make a placeholder for each of these pieces, and then start filling in the content and styling, one at a time.

## Use Research and Documentation to Solve Specific Problems

No matter how experienced you are, you will always face challenges that are new to you and outside the scope of your training. When this happens, it is time do some research to learn new approaches and skills to solve the problem at hand. For example, If you were building App Academy's landing page, you might need to do some research to figure out how to convert the options in the navigation bar to the drop-down menu on the mobile design. Sometimes you will need to look at the documentation to learn new syntax; other times you might need to learn how to use a new library or tool that might help you solve the problem.

## How to read the documentation

Reading documentation may sound straightforward, but some concepts can be a little more confusing than others. A few tips that can help give you a better grasp of the concepts are:

1. Read it slowly, and then read it again
2. Look at the examples
3. Type out the code yourself, and experiment with it

## Debugging HTML

Errors can vary drastically depending on what language you are using. Whenever you run into an error that you are unfamiliar with, you should do your research to try to understand what kind of error it is and how to solve it. HTML won't always give you a straightforward error message so it is worth noting the most common HTML errors:

1. Unclosed elements
2. Badly nested elements
3. Unclosed Attributes

The [Debugging HTML Docs](https://developer.mozilla.org/en-US/docs/Learn/HTML/Introduction_to_HTML/Debugging_HTML) has more information for you on the several different HTML errors that you may run into. Syntax errors and logic errors are also common to run into when coding HTML.
